# PptxEditor and Office.js API compatibility

This directory measures the public surface of `@pptx-editor.dev/editor-api` against the Office.js presentation API (the `PowerPoint` namespace of `@types/office-js`). The tooling is a port of DOCX Editor's `packages/editor-api/compat/` and `packages/editor-api/scripts/` at 5993bd223. Each such script names its DOCX Editor path and commit in its first lines.

## Informational presentation editing report

From the repository root, run:

```bash
bun run --filter '@pptx-editor.dev/editor-api' compat:report
```

The report checks only the presentation editing methods and property writes in `editing-scope.json`. It covers slides, shapes, text frames and text ranges, fonts and paragraph formats, fills and lines, tables, hyperlinks, tags, document properties, and page setup. Read-only APIs, navigation, range bounds, selection changes, export, host setup, lifecycle methods, enums, and option objects do not enter the denominator. Text replacement through a range is an edit; moving a range or the selection is not.

The upstream member identifier (UID) list defines the scope independently from the implemented subset. Unsupported editing calls stay in the denominator. Review this list when you adopt a new upstream pin or change the intended editing scope. A missing UID is an error; it never silently reduces the denominator. The full pinned inventory, `reference/presentation.full-inventory.json`, remains reference input, so scope changes do not need a network fetch.

The checker reads the actual exports of `src/index.ts` and follows re-exports and inheritance. A public class that the package exports under the Office.js class name, for example `Shape`, is compared with `PowerPoint.Shape`; the report maps `PowerPoint.Shape#fill` to `PptxEditor.Shape#fill`. Methods compare all overloads, parameters, and return signatures. Property writes compare setter types only. For example, a nullable `font.bold` getter does not reduce write compatibility if the setter accepts `boolean`. Read differences can still appear in runtime notes.

Read `compat/reports/report.md` for editing endpoints and runtime notes. `report.json` includes the comparison shapes under `expected` and `actual`, along with upstream metadata. `summary.md` contains the overall editing percentage and separate method and property-write percentages. Use `--output <directory>` with the package command to change the output directory.

Signature statuses are `match`, `different`, and `missing`. Each editing member counts once. An exact method match requires all overloads to match. Namespace, whitespace, quote, and union-order normalization preserve enum alternatives and inline object types. Named references remain named; this is not recursive structural assignability. Equivalent overload spellings or differently named aliases can appear as `different`. No percentage proves runtime equivalence.

Add per-endpoint observations to `runtime-notes.json`:

```json
{
  "PowerPoint.ShapeFill#setSolidColor": {
    "status": "partial",
    "notes": "Accepts #RRGGBB values only."
  }
}
```

Runtime statuses are `equivalent`, `partial`, `different`, `unsupported`, and `unverified`. Missing notes default to `unverified`. Use `equivalent` only after you review runtime behavior and tests. Notes never change signature scores. Notes outside the editing scope stay stored but do not appear in the editing report. A note on a UID that is not in the full inventory is an error.

Signature differences do not fail the command. Tooling errors exit nonzero and show no report.

## PptxEditor additions

Some public members can have no Office.js equivalent. They stay outside the manifest selection, the reports, and the scores. Never add them to `manifest.symbols`. If an addition fills a gap where Office.js has no member for the operation, also record the decision as an `omissions` entry.

Runtime infrastructure stays outside the editing scope too. Host creation and the batch runner belong to host setup. Edits inside a batch are ordinary Office.js calls, and the report counts them.

## Layout

| Path | What it is | Who writes it |
| --- | --- | --- |
| `manifest.json` | The allowlisted subset: which `PowerPoint.*` and `OfficeExtension.*` symbols and members are selected, the string enums that the selected members name, and every deliberate omission with its reason. | Hand-edited. |
| `editing-scope.json` | The editing methods and property writes that the report measures. | Hand-edited. |
| `runtime-notes.json` | Per-endpoint runtime observations. | Hand-edited. |
| `reference/presentation.reference.json` | Normalized facts extracted from the manifest-selected subset of one `@types/office-js` release. | Generated by `scripts/fetch-office-reference.mjs` (network). |
| `reference/presentation.full-inventory.json` | Normalized facts for every member of the `PowerPoint` and `OfficeExtension` namespaces of the pinned release. The report reads this file. | Generated by `scripts/fetch-signature-inventory.mjs` (network). |
| `provenance.json` | The upstream package, version, integrity hash, license, and source commit that produced the reference files, and when. | Generated by `scripts/fetch-office-reference.mjs` (network). |
| `definitely-typed-commits.json` | The reviewed DefinitelyTyped source commit for each adopted `@types/office-js` version. A version with no entry cannot be written into `provenance.json`. | Hand-edited, or by `--adopt` (network). |
| `type-assert.ts` | `IsExact` and `Expect`, the strict type-equality helpers that the generated assertions use. | Hand-edited (copied from DOCX Editor). |
| `generated/conformance.generated.ts` | One compile assertion for each selected member, against the real public types of `src/index.ts`. | Generated by `scripts/generate-conformance.mjs` (offline). |
| `fixtures/source-compat/*.ts` | Office.js presentation code with the namespace changed to `PptxEditor`. The compiler checks it; nothing runs it. | Hand-edited. |
| `tsconfig.json` | The project that compiles `type-assert.ts`, `generated/`, and `fixtures/` against the package sources. | Hand-edited. |

The manifest selects classes, interfaces, and functions. The reference extractor reads only those kinds, as in DOCX Editor. The `enums.names` list in `manifest.json` names the string enums that the selected members use. The public surface declares each as a string literal union type with the same name. Their values are `enum-member` rows in the full inventory.

Each selected class leaves out the `ClientObject` plumbing that every upstream class declares again: `context`, `isNullObject`, `load`, `toJSON`, `track`, and `untrack`. `ClientObject` itself selects `context` and `isNullObject`.

## Conformance assertions

The report compares signature text. The conformance check asks the compiler. From the repository root, run:

```bash
bun run --filter '@pptx-editor.dev/editor-api' compat:generate
```

The command writes `generated/conformance.generated.ts` from `manifest.json` and `reference/presentation.full-inventory.json`. The full inventory keeps the enum names, for example `ShapeType`, which the subset reference collapses to string literals. Each selected member gets one assertion:

- A method compares all its overloads, in reference order, with the real member, for example `PptxEditor.ShapeCollection['addTextBox']`.
- A property compares its read type, `readonly`, and `?` with `Pick` of the real class, for example `Pick<PptxEditor.Shape, 'fill'>`.
- A writable property also gets a write check: the reference write type must assign to the real setter. TypeScript has no type operator for a setter type, so this check goes in one direction only. The report compares setter types exactly.

`IsExact` checks both directions, so a narrower or a wider type fails. A reference type names the package export of the same name, so a missing export fails as a compiler error. The file depends only on committed compat data, never on the package sources, so an API change never makes the file stale. The compiler finds the drift.

There is no hand-written declaration file, unlike DOCX Editor's `packages/editor-api/compat/docxeditor/declarations.ts`. The assertions import the shipped types, so the check cannot drift from the API.

A selected member that cannot match exactly goes in `manifest.conformanceExceptions`, with its reason. The generated file names the entry and its reason in place of the assertion. The generator refuses an exception that names a member the manifest does not select. Add an exception only for a deliberate difference, never to make the check pass.

`scripts/__tests__/conformance.test.ts` compiles `tsconfig.json` with zero diagnostics, checks that the committed file is current, and shows that a drifted declaration or a drifted reference fails its assertion. To check only that the committed file is current, run `compat:generate -- --check`.

The source-compatibility fixtures adapt Office.js presentation examples for `PptxEditor` and `PptxEditorServerRuntime`. They also adjust values, collection access, and property loads for compile-time checks. The [fixture source notes](fixtures/source-compat/README.md) record pinned Microsoft examples, adaptation details, and the MIT license scope.

## Offline compatibility checks

Compatibility tests and reports read committed reference data. They do not fetch the upstream declarations during installation, builds, or tests. Only the explicit maintenance commands below fetch upstream data. `scripts/__tests__/compat-tooling.test.ts` checks the manifest, the editing scope, and the report function offline.

The commands record normalized facts and source provenance, never the upstream declaration files.

## Regenerating

Run these commands from `packages/editor-api`:

```bash
# Network: refresh reference/presentation.reference.json and provenance.json
# from the pinned release. Without --version, the command reads the current
# "latest" release (`bun run compat:fetch-reference`), which needs a reviewed
# pin in definitely-typed-commits.json.
node scripts/fetch-office-reference.mjs --version 1.0.605

# Network: refresh reference/presentation.full-inventory.json from the
# release recorded in provenance.json. Run it after compat:fetch-reference.
bun run compat:fetch-inventory

# Network: check whether the upstream release has drifted from the checked-in
# reference, without overwriting anything (exit code 1 on drift).
bun run compat:check-drift

# Network: adopt an upstream release whose reference differs in nothing but
# the version string. Refuses (exit code 1) when anything else differs.
node scripts/fetch-office-reference.mjs --adopt
```

The fetch commands download the pinned npm tarball and verify its `dist.integrity` before they parse it.

### Remove a selected member

If you remove a member from `manifest.json`, also remove it from `reference/presentation.reference.json`. A member removal is the only permitted manual edit to the reference. Use the fetch command to add members or change upstream signatures.

### Review upstream drift

`compat:check-drift` compares the latest published `@types/office-js` version without writing files. If its source commit has not been reviewed, the output starts with `REVIEW REQUIRED:`. Record the exact DefinitelyTyped commit in `definitely-typed-commits.json` before you run `compat:fetch-reference`.

Automatic adoption with `--adopt` requires both checks:

- The complete normalized references match, excluding only `generatedFrom.version`.
- The source commit's `index.d.ts` blob hash matches the file in the integrity-verified npm tarball.

## Why three layers of comparison

`scripts/lib/shape-compare.mjs` compares normalized signatures per overload, for upstream drift. It does not use one-way TypeScript assignability, which can accept wider or narrower types. `scripts/compat-report.mjs` compares the compiler's view of the actual package exports with the full inventory, for the editing report. `generated/conformance.generated.ts` makes the compiler prove type identity for every selected member, editing or not, and the source-compatibility fixtures prove that Office.js call patterns compile.

### Formatting extensions

`Shape.getFormat()`, `Shape.patchFormat()`, `ShapeLineFormat.beginArrowheadStyle`, `ShapeLineFormat.endArrowheadStyle`, and `ShapeArrowheadStyle` are SDK extensions. They are not entries in the pinned Office.js PowerPoint reference or compatibility manifest. Endpoint values use PascalCase. `Open` maps to DrawingML `arrow`. The endpoint names do not imply Office.js PowerPoint compatibility.
