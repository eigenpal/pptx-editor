Queue operations inside `runtime.run()`, then execute them with `context.sync()`. Proxy properties contain values only after a load completes.

## Load, read, and write

This function trims shape names on the first slide. It accepts an open runtime:

```ts
import type { PptxEditorRuntime } from '@pptx-editor.dev/editor-api';

export async function trimNames(runtime: PptxEditorRuntime) {
  await runtime.run(async (context) => {
    const shapes = context.presentation.slides.getItemAt(0).shapes;
    shapes.load('items/name');
    await context.sync();
    for (const shape of shapes.items) {
      shape.name = shape.name.trim();
    }
    await context.sync();
  });
}
```

The first sync fills the collection and its names. The second sync applies all name writes together. Keep synchronization outside item loops. Always synchronize queued writes before returning from the callback. Calls left queued when the callback returns do not apply.

## Select properties explicitly

Use `load('name')` for one property and `load('items/name')` for collection items. Navigation paths also work, such as `load('shapes/items/name')` on a slide. Each collection level needs another host batch; items at one level load together.

`load({ select, top, skip })` supports collection queries. `load()` and `load('items')` load every scalar property of each item. `$all` loads scalar properties but does not load navigation properties. Load only the values your task needs.

Reading before loading throws `PropertyNotLoaded`. Invalid load paths throw `InvalidArgument` immediately and queue nothing. Existing queued calls remain queued after that load error.

## Check optional objects

Use `getItemOrNullObject()` when a target can be absent:

```ts
// context belongs to the active run; slideId identifies a slide.
const slide = context.presentation.slides.getItemOrNullObject(slideId);
slide.load('id');
await context.sync();
if (slide.isNullObject) return;
slide.moveTo(0);
await context.sync();
```

Check `isNullObject` after synchronization. Writing to a null object is refused. Use `getItem()` when absence should fail with `ItemNotFound`.

## Understand commit boundaries

A batch of independent writes is atomic: all writes apply or none apply. However, a single `sync()` can contain multiple host batches. A dependent lookup can split synchronization after earlier writes have committed. Collection reads queued after writes can also fail after those writes apply.

A failure after a split retains the earlier writes. Its diagnostic hint identifies that boundary. The diagnostic `edit.read-after-commit` also means writes applied before a read failed. Do not replay the whole sync after either failure.

Queue collection loads before writes when they share a sync. For explicit boundaries, complete the reads in one sync and then queue writes in another. In a live editor, one sync that writes remains one undo step, including a split sync.

## Recover from errors

Check `isPptxEditorError(error)` before using the stable `code`. This function returns an explicit stale result for the caller to reconsider:

```ts
import { isPptxEditorError, type PptxEditorRuntime } from '@pptx-editor.dev/editor-api';

export async function normalizeName(runtime: PptxEditorRuntime) {
  try {
    await runtime.run(async (context) => {
      const shape = context.presentation.slides.getItemAt(0).shapes.getItemAt(0);
      shape.load('name');
      await context.sync();
      shape.name = shape.name.trim();
      await context.sync();
    });
    return { ok: true as const };
  } catch (error) {
    if (isPptxEditorError(error) && error.code === 'StaleDocument') {
      return { ok: false as const, reason: 'stale' as const };
    }
    throw error;
  }
}
```

This example requires a first slide with a shape. After `StaleDocument`, read again and reconsider the edit. Do not blindly retry a model-generated replacement. To avoid the error in jobs that edit one presentation at the same time, see [Run parallel work](#run-parallel-work).

| Code | Action |
| --- | --- |
| `PropertyNotLoaded`, `ValueNotLoaded` | Load or synchronize before reading |
| `InvalidArgument` | Correct the argument or load path |
| `ItemNotFound` | Find the target again or handle its absence |
| `NotSupported`, `NotImplemented` | Choose an operation supported by this host and content |
| `StaleDocument` | Read the changed presentation and reconsider the write |
| `InvalidObjectPath`, `ObjectInUse`, `InvalidRequestContext` | Correct proxy ownership or lifetime |
| `RuntimeDisposed` | Create a new runtime |
| `ResourceLimitExceeded`, `DocumentUnavailable` | Inspect input or host availability |
| `GeneralException` | Inspect the diagnostic and underlying failure |

Most invalid operation arguments are reported at the next sync. Invalid loads, unloaded property reads, and invalid object lifetimes can throw immediately. `error.debugInfo.innerError` provides a stable engine diagnostic when available. Error messages do not contain presentation content.

A refused batch drops its queued calls. Existing proxies remain usable within their run. After correcting a known argument error, queue only the corrected operations again. Recreate objects that the refused batch would have added; those objects never existed.

## Run parallel work

Runs on one runtime do not wait for each other. The presentation has one revision for all of its content, so writes to two different slides still conflict. When two runs read, wait, and then write, the later write refuses with `StaleDocument`.

### Do slow work outside `run()`

Do slow work, such as a model call, outside `run()`. Send every run for one presentation through one queue, so that only one run is active at a time. Keep each queued run short: it reads, decides, and writes. This function rewrites the text of some shapes with one model call for each shape:

```ts
import {
  isPptxEditorError,
  type PptxEditorRuntime,
  type RequestContext,
} from '@pptx-editor.dev/editor-api';

export interface TextTarget {
  readonly slideId: string;
  readonly shapeId: string;
}

// One queue for each runtime. A task starts when the task before it settles.
const queues = new WeakMap<PptxEditorRuntime, Promise<unknown>>();

export function enqueue<T>(runtime: PptxEditorRuntime, task: () => Promise<T>): Promise<T> {
  const result = (queues.get(runtime) ?? Promise.resolve()).then(task);
  const settled = result.catch(() => undefined);
  queues.set(runtime, settled);
  return result;
}

// Run a task again after StaleDocument, at most maxAttempts times in total.
async function retryStale<T>(task: () => Promise<T>, maxAttempts = 3): Promise<T> {
  for (let attempt = 1; ; attempt += 1) {
    try {
      return await task();
    } catch (error) {
      if (!isPptxEditorError(error) || error.code !== 'StaleDocument') throw error;
      // No revisions: earlier writes of that sync applied. Do not run it again.
      if (error.expectedRevision === undefined) throw error;
      if (attempt >= maxAttempts) throw error;
      console.warn('StaleDocument: reading again', {
        attempt,
        expectedRevision: error.expectedRevision,
        actualRevision: error.actualRevision,
      });
    }
  }
}

// A target whose slide or shape is gone reads as null after the sync.
function loadTexts(context: RequestContext, targets: readonly TextTarget[]) {
  return targets.map((target) => {
    const slide = context.presentation.slides.getItemOrNullObject(target.slideId);
    const shape = slide.shapes.getItemOrNullObject(target.shapeId);
    const range = shape.textFrame.textRange.load('text');
    return { target, text: () => (shape.isNullObject ? null : range.text), range };
  });
}

export async function rewriteTexts(
  runtime: PptxEditorRuntime,
  targets: readonly TextTarget[],
  rewrite: (text: string) => Promise<string>
) {
  // 1. Read every target in one short run.
  const before = await retryStale(() =>
    enqueue(runtime, () =>
      runtime.run(async (context) => {
        const items = loadTexts(context, targets);
        await context.sync();
        return items.map((item) => item.text());
      })
    )
  );
  // 2. Do the slow work outside run(), in parallel. A failed call gives null.
  const outcomes = await Promise.allSettled(
    before.map((text) => (text === null ? Promise.resolve(null) : rewrite(text)))
  );
  const after = outcomes.map((outcome) => (outcome.status === 'fulfilled' ? outcome.value : null));
  // 3. Apply every result in one run. Read again, and write only where the text is unchanged.
  return retryStale(() =>
    enqueue(runtime, () =>
      runtime.run(async (context) => {
        const items = loadTexts(context, targets);
        await context.sync();
        const skipped: TextTarget[] = [];
        items.forEach((item, index) => {
          const result = after[index];
          if (typeof result === 'string' && item.text() === before[index]) item.range.text = result;
          else skipped.push(item.target);
        });
        await context.sync();
        return { skipped };
      })
    )
  );
}
```

The function returns the targets that it did not write. Another writer changed or deleted them, or their model call failed. Read them again before you decide. Each target shape must have a text frame. For example, a picture or a group refuses with `NotSupported`.

The queue prevents conflicts between the runs that use it. Other writers can still change the presentation between a read and a write:

- a user of the editor
- a collaborator
- another runtime
- a run outside the queue

The retry reads again and checks each target before it writes. Keep the retry bounded. Do not repeat the slow work in the retry. Do not call `enqueue` from a queued task for the same runtime. The inner task then waits forever for the outer task.

### Know when a sync checks the revision

Each commit increments the revision. These changes commit:

- a write from any run
- an edit in the editor
- a change from a collaborator
- an undo or a redo

A sync sends its calls in one or more host batches. These rules apply:

- The context records the revision after each host batch that succeeds. Batches that only read also record it.
- A host batch that writes requires the recorded revision. If the presentation changed, that batch refuses with `StaleDocument` and applies nothing.
- The first host batch of a run has no recorded revision, so it does not check.
- A sync can read in several host batches, for example `load('items/name')` on a collection. Then its later batches require the revision of its first batch. This applies to writes and to reads. A write from another run between those batches makes the sync refuse with `StaleDocument`.
- A run that adopts a tracked object also adopts the revision of the earlier run. Then its first write also checks.

Thus a run that reads, waits for slow work, and then writes can fail. If another run writes during that wait, the later write refuses with `StaleDocument`.

### Log a stale write

On `StaleDocument`, `error.expectedRevision` is the revision that the context recorded. `error.actualRevision` is the revision of the presentation at the refusal. Log both to see how many commits came in between. They can be `undefined` when the refusal comes after earlier writes of the same sync applied. Do not replay that sync; see [Understand commit boundaries](#understand-commit-boundaries). Revisions are counters for one open presentation. The file does not store them.

## Keep proxies within their lifetime

Return plain values from a run for use in jobs, UI state, or model requests. To retain a proxy deliberately, call `context.trackedObjects.add(object)` during its run. Adopt it with `runtime.run(object, callback)` in a later run and remove it when finished.

Await each sync. Concurrent sync calls execute in order, but each rejected promise still needs error handling.
