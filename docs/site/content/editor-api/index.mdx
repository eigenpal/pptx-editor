`@pptx-editor.dev/editor-api` edits PPTX files through a supported subset of the Office.js presentation object model: `Presentation`, `Slide`, `Shape`, `TextFrame`, `TextRange`, `Table`, and their collections. It runs on a server over PPTX bytes, or in the browser against an editor that is already open.

## Install and edit a presentation

Install the API and its engine peer dependency:

```bash
npm install @pptx-editor.dev/editor-api @pptx-editor.dev/core
```

The following server example adds a title box to the first slide, fills a table cell, and saves the result:

```ts
import { readFile, writeFile } from 'node:fs/promises';
import { PptxEditor } from '@pptx-editor.dev/editor-api';

const runtime = await PptxEditor.createServer(await readFile('deck.pptx'));
try {
  await runtime.run(async (context) => {
    const slide = context.presentation.slides.getItemAt(0);
    const box = slide.shapes.addTextBox('Quarterly results', { left: 40, top: 40, width: 400 });
    box.textFrame.textRange.font.bold = true;
    const table = slide.shapes
      .addTable(2, 2, {
        values: [
          ['Region', 'Total'],
          ['North', '42'],
        ],
      })
      .getTable();
    await context.sync(); // One atomic batch: all of the writes, or none.

    const cell = table.getCellOrNullObject(1, 1);
    cell.horizontalAlignment = 'Right';
    cell.fill.setSolidColor('#FFF2CC');
    await context.sync();
  });
  await writeFile('deck.edited.pptx', await runtime.save());
} finally {
  runtime.dispose();
}
```

## Choose a host

| Host | Factory | Save through | Selection |
| --- | --- | --- | --- |
| Server | `PptxEditor.createServer(bytes, options?)` | `runtime.save()` | No |
| Browser | `PptxEditor.createBrowser(editor)` from `@pptx-editor.dev/editor-api/browser` | The editor that owns the document | Yes |

`createServer` takes the font options of the engine: `fonts` adds faces to measure text with, and `substitutes` loads the metric-compatible substitute fonts (default `true`). Text writes re-fit each text body by its autofit rule, so the saved layout matches the editor.

`createBrowser` borrows a `PptxEditorInstance`. Each `sync()` that writes is one undo step in that editor. Undo goes back to the slide and the selection that the reader had before the sync. A browser runtime has no `save()`, and it refuses writes while the editor is open for viewing. Dispose the runtime before the editor.

Read `runtime.capabilities` to check a host before you call a member that needs it, for example `capabilities.selection` before `getSelectedShapes()`, or `capabilities.images` before `getImageAsBase64()`.

## Draw pictures on a server

A browser runtime draws `getImageAsBase64` pictures on a canvas. A server has no canvas, so pass a `rasterize` function to `createServer`. The engine paints the picture with the editor's own renderer into a standalone SVG document, and your function turns that SVG into PNG bytes. The package ships no rasterizer, so choose one that fits your server, for example an SVG rasterizer library or a headless browser.

The function gets `svg`, `width`, `height`, and `fonts`, and must answer a PNG of exactly `width` by `height` pixels. The SVG holds its pictures as data URLs and its fonts as `@font-face` rules. Each entry of `fonts` gives the `family` name that the SVG uses and the font bytes, for a rasterizer that does not read CSS fonts. Use the font bytes for that picture only: do not store them, cache them, or write them to disk. A rasterizer with a process-wide font registry must remove the faces before it returns, as the example does. Each `family` name is unique for each open presentation, so the faces of two presentations never collide.

This example uses the `@napi-rs/canvas` package:

```ts
import { createCanvas, GlobalFonts, loadImage } from '@napi-rs/canvas';
import { PptxEditor } from '@pptx-editor.dev/editor-api';

const runtime = await PptxEditor.createServer(bytes, {
  rasterize: async ({ svg, width, height, fonts }) => {
    // Register the faces for this picture only, and remove them before returning.
    const keys = fonts.map((font) => GlobalFonts.register(Buffer.from(font.bytes), font.family));
    try {
      const canvas = createCanvas(width, height);
      canvas.getContext('2d').drawImage(await loadImage(Buffer.from(svg)), 0, 0, width, height);
      return new Uint8Array(canvas.toBuffer('image/png'));
    } finally {
      for (const key of keys) if (key) GlobalFonts.remove(key);
    }
  },
});
```

A rasterizer that throws, or that answers something other than a PNG of the asked size, refuses the sync with `GeneralException` and the diagnostic `image.failed`.

## Batches and loads

- Calls on proxy objects are queued. Nothing reaches the presentation until `await context.sync()`.
- One `sync()` is one atomic batch. If one call is refused, no write of that batch applies.
- Every read and lookup sees the calls queued before it in the same `sync()`, for example `getItemOrNullObject` after an `add`, or `getSelectedShapes()` after `setSelectedShapes`. When a later call needs the answer of such a read to go on, for example a write to a `getItemOrNullObject` result or to the selected text, the sync splits before that read: the calls before it apply first. On a live editor, the whole sync is still one undo step. A refusal after the split keeps its own diagnostic, and its hint says that the writes before the read applied.
- A call with an argument that the API does not accept does not throw. The next `sync()` refuses with `InvalidArgument`, `NotImplemented`, `NotSupported`, or `ItemNotFound`, and no call of that batch applies, as in Office.js. For example, a write of `ShadeFromTitle` or a bad `addTable` option refuses at the sync. A refused call that returns an object returns one that takes more calls and queues nothing.
- Only three errors throw at the call: a read of a property that you did not load (`PropertyNotLoaded`), a bad `load(...)` argument, and an object or context that you use after its run. A bad `load(...)` argument includes a wrong name anywhere in a path, also below the items of a collection: `shapes.load('itmes/name')` throws `InvalidArgument` with the hint "Did you mean 'items'?". Such a call queues nothing, and the calls before it stay queued.
- A refused sync drops only its own calls. Proxies stay usable, as in Office.js: a retry with the same objects works while the objects exist. An object that the refused sync would have created does not exist, and refuses with `InvalidObjectPath`.
- An object that a call creates is usable in the same batch: `addTextBox(...)` followed by `box.name = 'Title'` is one sync.
- A `sync()` that you call before the previous one settles takes the calls queued so far. It sends them when the previous sync settles. Syncs apply in the order you call them. A refused sync rejects alone: the syncs after it still apply. A sync that you do not await still applies before the run ends. If such a sync is refused and you do not catch it, its rejection is unhandled.
- Calls that are still queued when the callback returns do not apply. In development builds, `run()` prints a warning when any of them is a write. The warning also names each argument error that the missing `sync()` would have given.
- Read a property only after a `load(...)` for it completed in a `sync()`. An earlier read throws `PropertyNotLoaded`.
- A name that is not a property refuses with `InvalidArgument`. Its message suggests the nearest property name and lists every name the object loads.
- `load(...)` takes paths through navigation properties and collections, for example `slide.load('shapes/items/textFrame/textRange/text')`. It also takes the property tree, for example `slide.load({ shapes: { items: { name: true } } })`, and `expand` and `$all`. `$all` loads every scalar property of an object, and no navigation property.
- Collections take `load('items/name')` and `load({ select, top, skip })`. `load()` and `load('items')` load every scalar property of each item. The items of one collection are read together, so a load costs one round trip for each level of collections on its path, not one for each item. In a sync that writes, put such a load before the writes. The item reads then go before the writes, which stay one atomic batch. An item read that goes after the writes and fails refuses with the diagnostic `edit.read-after-commit`: the writes applied, so do not apply them again.
- `getItemOrNullObject` and `getCellOrNullObject` answer an object with `isNullObject` set when the item does not exist. `getItem` refuses with `ItemNotFound`.
- A lookup whose answer is not an object, such as a null-object check, cannot depend on a write of the same sync. Sync after the write, then look up the item.
- A write that follows a read in the same run applies only if the presentation did not change after that read. If another writer changed it, the batch refuses with `StaleDocument` and applies nothing.
- Proxies end with their run. To keep one, call `context.trackedObjects.add(object)`, then pass it to a later `runtime.run(object, callback)`.

## Common mistakes

These four mistakes cause most first errors.

**A read with no load.** A proxy holds no values until a `sync()` fills them. Load the properties first, then sync, then read:

```ts
const box = slide.shapes.getItem('2');
box.load('name');
await context.sync();
console.log(box.name); // A read before the sync throws PropertyNotLoaded.
```

**A sync inside a loop.** Each `sync()` is one round trip and, on a live editor, one undo step. Queue the work for every item, then sync once:

```ts
const shapes = slide.shapes.load('items/name');
await context.sync();
for (const shape of shapes.items) shape.name = shape.name.trim();
await context.sync(); // One sync for all the writes.
```

**A retry after a refusal.** A refused `sync()` applies nothing and drops only its own calls. Objects that you looked up before it still work, so queue the corrected calls again and sync. An object that the refused sync would have created was never created: create it again.

```ts
try {
  box.fill.setSolidColor('notacolor');
  await context.sync();
} catch {
  box.fill.setSolidColor('#1F4E79'); // The same proxy works in the retry.
  await context.sync();
}
```

**Bindings in a saved file.** A binding lives in memory, for the lifetime of the runtime. It is not saved, so a presentation that you open again has no bindings. Add them again after you open it. A binding whose shape is deleted stays listed, and `getShape()` refuses with `ItemNotFound`.

## Handle errors

Every refusal is a `PptxEditorError`. Test for one with `isPptxEditorError(error)`, and branch on `error.code`:

| Code | Cause |
| --- | --- |
| `PropertyNotLoaded`, `ValueNotLoaded` | A read before the `sync()` that fills it |
| `InvalidArgument` | An argument or a load option that the API does not accept |
| `ItemNotFound` | No such item in the collection |
| `NotSupported` | The call is outside the subset for this host or content, for example a selection on a server |
| `NotImplemented` | The member has the Office.js shape, but this package does not implement it |
| `StaleDocument` | Another writer changed the presentation after this context read it |
| `InvalidObjectPath`, `ObjectInUse`, `InvalidRequestContext`, `RuntimeDisposed` | A proxy or a context used outside its lifetime, or a write to a null object |
| `ResourceLimitExceeded`, `DocumentUnavailable`, `GeneralException` | The presentation or the host refused the request |

`error.debugInfo.innerError` gives a fixed engine diagnostic when one applies, for example `host.no-selection`, `edit.null-object`, `edit.last-slide`, `edit.group-parent`, `edit.merge-overlap`, `edit.read-after-commit`, or `sync.object-from-refused-sync` (a call on an object that a refused sync would have created). An `InvalidArgument` for a value outside what the API accepts has the diagnostic `argument.not-accepted`, and its message names what is accepted, for example the values of an enum, with the nearest value when the argument looks like a typo of one. A message never contains presentation content.
